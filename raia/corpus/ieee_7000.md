# IEEE 7000-2021 — Value-Based Engineering (Curated Summary)

> **Authority level: STANDARD.** Curated summary for RAG grounding, prepared
> for the RAIA proof of concept. IEEE 7000-2021 ("IEEE Standard Model Process
> for Addressing Ethical Concerns during System Design") is a paywalled
> standard; this summary covers its publicly documented process model and
> terminology. Verify against the official standard: https://standards.ieee.org

## Purpose

IEEE 7000 defines a model process by which organizations can translate
stakeholder values and ethical concerns into concrete system requirements
during concept exploration and design — the approach is called
**Value-Based Engineering (VBE)**. It targets systems engineers, product
managers, and organizational leadership, and is designed to integrate with
existing development processes (including agile).

## Key Concepts and Terminology

- **Core values**: fundamental values elicited from stakeholders for the
  system's context of use (e.g. fairness, autonomy, privacy, transparency,
  care). VBE recommends prioritizing a small set of core values.
- **Value cluster**: a core value together with adjacent, instrumental
  values that support it (e.g. transparency supporting accountability).
- **Value demonstrator**: a concrete illustration of how a value manifests
  (positively or negatively) in the system's context of use.
- **Ethical Value Requirement (EVR)**: an organizational or technical
  requirement derived from a value disposition, written so that it can be
  traced, implemented, and verified like any other requirement.
- **Value Register**: the living document that records elicited values,
  their prioritization, associated risks, and the EVRs derived from them,
  maintained with traceability across the lifecycle.
- **Context of Use**: the operational environment, stakeholders, and
  conditions in which the system will operate — value elicitation is always
  relative to a context of use.

## The Three Main Process Phases

### 1. Concept of Operations and Context Exploration

Characterize the system's context of use and its stakeholders — including
indirect stakeholders who do not use the system but are affected by it.
Outputs: context-of-use descriptions and a stakeholder register.

### 2. Ethical Values Elicitation and Prioritization

Elicit values from direct and indirect stakeholders through structured
reflection (drawing on utilitarian, duty/deontological, and virtue-ethics
perspectives to broaden the analysis). Identify value demonstrators,
cluster values, prioritize core values, and record everything in the Value
Register. Leadership commits to the prioritized values.

### 3. Ethical Requirements Definition (Value-Based Requirements Engineering)

Translate prioritized values into **Ethical Value Requirements (EVRs)** and
then into system requirements: each EVR must be traceable back to the value
and forward to design decisions, implementation artifacts, and verification
evidence. Risk-based design treatment: for each value, analyze threats
(how the design could harm the value) and opportunities (how it could
advance it), and derive requirements that mitigate threats.

## Traceability and Transparency Management

IEEE 7000 requires end-to-end traceability: value → EVR → system
requirement → design element → verification result. This traceability chain
is what makes ethical claims auditable rather than rhetorical. The standard
also calls for a Transparency Management process so that relevant
information about the system's ethical treatment is available to
appropriate stakeholders.

## Writing Good EVRs (Practical Guidance)

A well-formed EVR is:

1. **Traceable** — names the core value it protects and the stakeholder(s)
   affected.
2. **Verifiable** — phrased so that a test, audit, measurement, or
   inspection can determine whether it is met (e.g. "selection outcomes
   shall be auditable per protected attribute" rather than "the system
   shall be fair").
3. **Contextual** — bound to the documented context of use.
4. **Prioritized** — linked to the value prioritization recorded in the
   Value Register, so trade-off discussions reference an explicit ranking
   rather than ad-hoc judgment.

## Relationship to Other Frameworks

IEEE 7000 is strongest at design time (concept and requirements phases) and
does not prescribe post-deployment monitoring. In an SDLC-wide toolchain it
pairs naturally with lifecycle risk frameworks (e.g. NIST AI RMF) for
operations, and with requirement-specificity standards (e.g. Microsoft RAI
Standard v2) for verifiable acceptance criteria.
